# Owasps-JuiceShop-Penetration-Testing

# OWASP Juice Shop Web Security Assessment with OWASP ZAP

A hands-on web application security lab using **OWASP Juice Shop**, **OWASP ZAP**, **Firefox**, and **Kali Linux**.

The goal of this project was to build practical experience with web application testing by running a deliberately vulnerable application locally and routing browser traffic through an intercepting proxy. The project focuses on understanding how web traffic moves between a browser and an application, how requests and responses can be observed, and how ZAP can be used as part of a basic web security assessment workflow.

> **Lab only:** OWASP Juice Shop is intentionally vulnerable and is designed for security training. This project was performed against a local instance (`localhost:3000`) and is not intended for testing systems without permission.

---

## Project Overview

For this lab, I set up the OWASP Juice Shop in a Kali Linux environment and accessed it locally through a web browser.

I then used **OWASP ZAP (Zed Attack Proxy)** to explore the application and observe the traffic generated by the browser.

The screenshots included in this project show:

- OWASP Juice Shop running locally at `http://localhost:3000`
- OWASP ZAP being used for manual exploration
- Firefox selected as the browser to launch through ZAP
- The Juice Shop application being accessed successfully
- HTTP/WebSocket activity appearing inside ZAP
- The application being monitored from the ZAP Sites/History areas

This project is part of my practical cybersecurity learning path, with a focus on **web application security, offensive security, network traffic analysis, and security tooling**.

## Objectives

The main objectives of the project were to:

1. Understand the basic workflow of a web application security assessment.
2. Run a deliberately vulnerable web application in a controlled lab.
3. Configure and use OWASP ZAP as an intercepting proxy.

```text
+-------------------+

+---------+---------+
          |
          v
+-------------------+
|    Firefox        |

+---------+---------+
          |

          v
```

The important part of the setup is that the browser's traffic passes through ZAP before reaching the local Juice Shop instance. This makes it possible to inspect the application's communication rather than treating the browser and application as a black box.

## Project Workflow

### 1. Start the Lab Environment

The first step was to start the Kali Linux virtual machine through Oracle VirtualBox.

The security tools were then accessed from inside Kali Linux.

### 2. Start OWASP Juice Shop

The Juice Shop was made available locally and accessed through:

```text
http://localhost:3000
```

The screenshots confirm that the application was reachable from Firefox at this local address.

### 3. Open OWASP ZAP

OWASP ZAP was launched and configured for manual application exploration.

The ZAP interface shown in the project uses version **2.17.0**.

### 4. Configure Manual Explore

Inside ZAP, the **Manual Explore** section was used.

The target URL was:

```text
http://localhost:3000
```

Firefox was selected as the browser to launch for the exploration session.

This is useful because it allows the browser session to be routed through ZAP without having to manually configure every browser proxy setting from scratch.

### 5. Browse the Application

Once Firefox was launched through ZAP, the Juice Shop application was opened and browsed normally.

This stage is important because application behavior creates traffic that ZAP can observe.

For example, loading pages, navigating through the application, and interacting with application features can generate:

- HTTP requests
- HTTP responses
- API calls
- WebSocket communication
- Cookies
- Headers
- Parameters
- Other application-level traffic

### 6. Review Traffic in ZAP

The ZAP interface showed the application under the **Sites** section.

The project screenshots also show traffic in the ZAP history/WebSocket area.

This provided practical experience with the relationship between:

```text
Browser action
      ↓
HTTP/WebSocket request
      ↓
ZAP
      ↓
Juice Shop
      ↓
HTTP/WebSocket response
      ↓
Browser
```

## Key Security Concepts Practiced

### Intercepting Proxy

An intercepting proxy sits between the client and server.

Instead of:

```text
Browser  ----------------->  Web Server
```

the communication becomes:

```text
Browser  ----->  Proxy  ----->  Web Server
Browser  <-----  Proxy  <-----  Web Server
```

This allows a security tester to inspect and, where appropriate in an authorized lab, modify traffic.

---

### HTTP Request

An HTTP request is sent by the client to the server.

A simplified example:

```http
GET /rest/products/search?q=apple HTTP/1.1
Host: localhost:3000
```

A tester can inspect information such as:

- HTTP method
- URL/path
- Query parameters
- Headers
- Cookies
- Request body

---

### HTTP Response

The server sends a response back to the browser.

A simplified example:

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

The response can contain:

- Status code
- Headers
- Cookies
- HTML
- JSON
- JavaScript
- Other application data

---

### WebSockets

WebSockets provide a way for a browser and server to maintain an ongoing communication channel.

Unlike a simple one-off HTTP request, WebSockets can support continuous two-way communication.

In this lab, ZAP's WebSocket history provided visibility into this type of traffic generated while interacting with the application.

## Why This Project Matters

This project was more than simply opening Juice Shop in a browser. The important part was understanding the workflow behind web application testing.

A security tester needs to know:

1. What the target application is.
2. How the application communicates with the browser.
3. What endpoints are being accessed.
4. What information is being sent to the server.
5. What information is returned.
6. Which technologies are being used.
7. Where further testing may be appropriate.

Using ZAP helped turn normal browser activity into something that could be observed and analyzed.

This is an important foundation before moving into deeper testing such as authentication testing, input validation testing, access-control testing, injection testing, and other OWASP-related techniques.
